How each technique works

Each one is tagged with how identifying it tends to be. In the results, values marked ~ change often (window size, battery level), so they're left out of both IDs. Values marked ● are part of your fingerprint.

Your connectionhigh

seen before any script runs

Before your browser asks for a page, it sets up an encrypted (TLS) connection and opens with a ClientHello: the TLS versions, ciphers, key exchanges and extensions it supports, in its own order. Over HTTP/2 it then sends its settings and request headers, again in its own order. Every server sees all of this, and none of it needs JavaScript or can be turned off in settings.

This is the one section that comes from the server: it reads the opening bytes of your connection and sends back what they show.

JA4 condenses the ClientHello into a short code. It's the same in normal and private windows, because both use the same TLS library, which is why it's part of the core ID. It's also very hard to fake, so bot-detection services lean on it: a script claiming to be Chrome but greeting the server like Python's TLS library is caught straight away. JA3 is the older version. Chrome now shuffles its extension order on every connection, so its JA3 changes constantly while its JA4, which sorts them first, stays put. The HTTP/2 fingerprint does the same for HTTP/2's opening settings and the order of the :method, :authority, :scheme and :path headers.

Navigator propertiesmedium

the oldest trick in the book

The navigator object describes your browser: its name and version (the user agent), operating system, preferred languages, number of CPU threads, rough memory size, and whether it has a touch screen. One of these isn't much to go on. Together they narrow you down fast: "Firefox 140 on Linux, 16 threads, preferred languages en-AU then de" is a small crowd.

Canvas fingerprintinghigh

first described in 2012

The page draws some text, an emoji and overlapping shapes on an invisible canvas, then reads back the pixels. You'd expect every computer to draw the same image. They don't. Your graphics card, its driver, your operating system's font smoothing and anti-aliasing all change the result by a few pixels. Those differences are invisible to you but very consistent on your machine, so a hash of the image works as an ID.

…
running
How it works 
const ctx = canvas.getContext("2d");
ctx.font = "14px Arial";
ctx.fillText("Cwm fjordbank glyphs vext quiz 😃", 2, 15);
// … more shapes, gradients and blend modes …
const id = hash(canvas.toDataURL());

The page draws the image twice. Some browsers (Brave, Firefox with fingerprinting protection, Safari in private mode) add tiny random noise to canvas reads. If the two hashes differ, your browser is doing that.

WebGLhigh

WebGL gives pages direct access to your graphics card for 3D. Many browsers will just tell a page the name of the card and its driver. Beyond that, every GPU has its own limits (largest texture, number of shader inputs) and supports its own list of extensions. Like the canvas test, the page can also render a shape with a small shader and hash the pixels, which differ subtly between GPUs.

WebRTClow

used to be high

WebRTC powers video calls, and to connect two people it gathers your network addresses. Until about 2019 this leaked your private LAN IP (like 192.168.1.23) to any page, even through a VPN. Modern browsers hide it behind a random ….local name. This page only gathers local candidates and contacts no outside server. A real tracker would also use a public STUN server to learn your public IP.

JavaScript engine quirkslow

great at catching liars

Each JavaScript engine (V8 in Chrome, SpiderMonkey in Firefox, JavaScriptCore in Safari) computes some maths functions with tiny differences in the last digit. Each also words its error messages its own way and supports a different set of APIs. None of this is very unique, but it reveals your real engine even when the user agent string is faked. Bot-detection services rely heavily on this.

Beyond this page

How to defend yourself

There are two strategies. You can blend in: make your browser look like everyone else's. Or you can randomise: give a slightly different answer each time so your fingerprint never stays the same. Hiding things (blocking scripts, faking an unusual user agent) often backfires, because being unusual is itself identifying.

  • Tor Browser blends in. Every user gets the same window size (rounded), fonts, time zone and user agent. It's the strongest option, but sites can usually tell you're using Tor.
  • Mullvad Browser applies Tor Browser's anti-fingerprinting, without the Tor network.
  • Brave randomises. It adds small per-site, per-session noise to canvas, WebGL and audio, so your hash differs on every site.
  • Firefox blocks known fingerprinting scripts by default, and adds randomisation in strict mode and private windows. The privacy.resistFingerprinting setting turns on Tor-style uniformity, but it breaks some sites.
  • Safari presents a simplified system profile to every site, and adds noise in private browsing.
  • Content blockers like uBlock Origin block many fingerprinting scripts by their address. This works whatever your fingerprint is.

The ad and fraud-prevention industries keep inventing new signals, and browsers keep closing them. No defence is perfect. Using a mainstream, up-to-date browser with its protections turned on goes a long way.

What this page can't show you

Some techniques need more than one page view, or a view of the network this server doesn't have. Real trackers use them all the time:

  • TCP/IP fingerprint (p0f). Before TLS even starts, the first TCP packet reveals your operating system through details like its initial TTL and window size. This server sits behind a proxy, so it never sees that packet.
  • HTTP/3 (QUIC). Browsers that use HTTP/3 send a different set of transport settings, which can be fingerprinted the same way as HTTP/2. This site only offers HTTP/2.
  • Behaviour. How you type, move the mouse and scroll.
  • Supercookies. Not fingerprints exactly, but IDs hidden in places cookie-clearing misses: favicon caches, HSTS flags, ETags. Browsers have closed most of these by giving each site its own cache.
