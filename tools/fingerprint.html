Browser fingerprint

a tool · how websites recognise you without cookies

Clear your cookies, open a private window, change your IP: many websites can still recognise you. They do it by asking your browser dozens of small questions. How big is your screen? Which fonts do you have? How does your graphics card draw this shape? Each answer is shared by lots of people. Put enough of them together, though, and the combination is often unique to you. That combination is a fingerprint.

This page runs the techniques that real fingerprinting scripts use, shows you what each one learns about your browser, and explains how it works. The probes run locally in your browser, and the results are never sent anywhere. The one exception is Your connection: the server reads how your browser connected and sends that back to you, without keeping it. This site has no analytics.

Try this: open this page in a private window, or after clearing your cookies, and compare the two IDs.

  • The exact ID stays the same: a tracker can link those visits trivially.
  • The exact ID changes: your browser is altering some answers. Firefox and Safari private windows, and Brave all the time, round off or randomise values like CPU threads and canvas pixels. That's a real defence, but only a partial one.
  • The core ID stays the same: this is why it's only partial. Real trackers don't need an exact match. They match fuzzily, mostly on signals that are hard to fake: GPU, time zone, language, OS, codecs. If most of those agree, the two visits probably came from the same person.

To see exactly which signals changed, use Compare two visits. Then try another browser on the same computer. Some signals (fonts, graphics card, screen) follow you across browsers too.

How to read the results: each section is tagged with how identifying it tends to be. Values marked ~ change often (window size, battery level), so they're left out of both IDs. Values marked ● are part of the core ID.

Your connection

identifying: high · seen before any script runs

Before your browser asks for a page, it sets up an encrypted (TLS) connection and opens with a ClientHello: the TLS versions, ciphers, key exchanges and extensions it supports, in its own order. Over HTTP/2 it then sends its settings and request headers, again in its own order. Every server sees all of this, and none of it needs JavaScript or can be turned off in settings.

This is the one section that comes from the server: it reads the opening bytes of your connection and sends back what they show. Nothing is kept.

JA4 condenses the ClientHello into a short code. It's the same in normal and private windows, because both use the same TLS library, which is why it's part of the core ID. It's also very hard to fake, so bot-detection services lean on it: a script claiming to be Chrome but greeting the server like Python's TLS library is caught straight away. JA3 is the older version. Chrome now shuffles its extension order on every connection, so its JA3 changes constantly while its JA4, which sorts them first, stays put. The HTTP/2 fingerprint does the same for HTTP/2's opening settings and the order of the :method, :authority, :scheme and :path headers.

Navigator properties

identifying: medium · the oldest trick in the book

The navigator object describes your browser: its name and version (the user agent), operating system, preferred languages, number of CPU threads, rough memory size, and whether it has a touch screen. One of these isn't much to go on. Together they narrow you down fast: "Firefox 140 on Linux, 16 threads, preferred languages en-AU then de" is a small crowd.

…
running
How it works 
navigator.userAgent          // "Mozilla/5.0 (X11; Linux x86_64) …"
navigator.languages          // ["en-AU", "en"]
navigator.hardwareConcurrency // 16
navigator.deviceMemory       // 8 (Chromium only, rounded)
navigator.maxTouchPoints     // 0 on most desktops

Ironically, the "Do Not Track" setting itself became a fingerprinting signal, because so few people turned it on.

User-Agent Client Hints

identifying: medium · Chromium only

Chromium-based browsers (Chrome, Edge, Opera, Brave) froze much of the user agent string to reduce passive fingerprinting. Instead, a page can now ask for details like the exact OS version, CPU architecture and device model. The detail is still there, but asking for it is visible, so browsers could limit or audit it.

Time zone and locale

identifying: medium

Your time zone tells a site roughly where you are, without asking for your location. If it doesn't match where your IP address says you are (say, you're on a VPN), that mismatch is a signal too. Date and number formatting show your regional settings.

Canvas fingerprinting

identifying: high · first described in 2012

The page draws some text, an emoji and overlapping shapes on an invisible canvas, then reads back the pixels. You'd expect every computer to draw the same image. They don't. Your graphics card, its driver, your operating system's font smoothing and anti-aliasing all change the result by a few pixels. Those differences are invisible to you but very consistent on your machine, so a hash of the image works as an ID.

…
running
How it works 
const ctx = canvas.getContext("2d");
ctx.font = "14px Arial";
ctx.fillText("Cwm fjordbank glyphs vext quiz 😃", 2, 15);
// … more shapes, gradients and blend modes …
const id = hash(canvas.toDataURL());

The page draws the image twice. Some browsers (Brave, Firefox with fingerprinting protection, Safari in private mode) add tiny random noise to canvas reads. If the two hashes differ, your browser is doing that.

WebGL

identifying: high

WebGL gives pages direct access to your graphics card for 3D. Many browsers will just tell a page the name of the card and its driver. Beyond that, every GPU has its own limits (largest texture, number of shader inputs) and supports its own list of extensions. Like the canvas test, the page can also render a shape with a small shader and hash the pixels, which differ subtly between GPUs.

…
running
How it works 
const gl = canvas.getContext("webgl");
const ext = gl.getExtension("WEBGL_debug_renderer_info");
gl.getParameter(ext.UNMASKED_RENDERER_WEBGL);
// "ANGLE (NVIDIA, NVIDIA GeForce RTX 3070 Direct3D11 …)"
gl.getSupportedExtensions();       // a long, GPU-specific list
gl.getParameter(gl.MAX_TEXTURE_SIZE);

WebGPU

identifying: high · the new frontier

WebGPU is WebGL's successor. It exposes the GPU vendor and architecture, plus a long list of feature flags and numeric limits. Researchers have also shown that timing how GPU work is scheduled can tell apart even identical models of graphics card. This page only reads the descriptive info.

How it works

Audio fingerprinting

identifying: medium · no speakers needed

The page builds a tiny sound: a tone fed through a compressor. It renders it silently in memory and adds up the samples. The floating-point maths in your browser's audio engine, CPU and OS give a slightly different number on different setups. Nothing is played, and no microphone is used.

…
running
How it works 
const ctx = new OfflineAudioContext(1, 5000, 44100);
const osc = ctx.createOscillator();
osc.type = "triangle";
osc.frequency.value = 10000;
const comp = ctx.createDynamicsCompressor();
osc.connect(comp).connect(ctx.destination);
osc.start();
const samples = (await ctx.startRendering()).getChannelData(0);
// sum a slice of samples → e.g. 124.04347527516074

Installed fonts

identifying: high

Sites can't list your fonts directly, but they can test for them. The page measures some text in a fallback font, then asks for it in, say, "Calibri" with that same fallback. If the width changes, Calibri is installed. Your fonts reveal your OS, and also any apps you've installed (Office, Adobe, coding tools) and languages you use.

…
running
How it works 
ctx.font = "72px monospace";
const base = ctx.measureText("mmmmmmmmmmlli").width;
ctx.font = '72px "Calibri", monospace';
const installed = ctx.measureText("mmmmmmmmmmlli").width !== base;

WebRTC

identifying: low today · used to be high

WebRTC powers video calls, and to connect two people it gathers your network addresses. Until about 2019 this leaked your private LAN IP (like 192.168.1.23) to any page, even through a VPN. Modern browsers hide it behind a random ….local name. This page only gathers local candidates and contacts no outside server. A real tracker would also use a public STUN server to learn your public IP.

JavaScript engine quirks

identifying: low · great at catching liars

Each JavaScript engine (V8 in Chrome, SpiderMonkey in Firefox, JavaScriptCore in Safari) computes some maths functions with tiny differences in the last digit. Each also words its error messages its own way and supports a different set of APIs. None of this is very unique, but it reveals your real engine even when the user agent string is faked. Bot-detection services rely heavily on this.

running
How it works 
Math.tan(-1e300)   // differs between engines
try { null.x } catch (e) { e.message }
// V8:   "Cannot read properties of null (reading 'x')"
// Gecko: "null has no properties"
// JSC:   "null is not an object (evaluating 'null.x')"

What this page can't show you

Some techniques need more than one page view, or a view of the network this server doesn't have. Real trackers use them all the time:

  • TCP/IP fingerprint (p0f). Before TLS even starts, the first TCP packet reveals your operating system through details like its initial TTL and window size. This server sits behind a proxy, so it never sees that packet.
  • HTTP/3 (QUIC). Browsers that use HTTP/3 send a different set of transport settings, which can be fingerprinted the same way as HTTP/2. This site only offers HTTP/2.
  • Behaviour. How you type, move the mouse and scroll.
  • Supercookies. Not fingerprints exactly, but IDs hidden in places cookie-clearing misses: favicon caches, HSTS flags, ETags. Browsers have closed most of these by giving each site its own cache.

How to defend yourself

There are two strategies. You can blend in: make your browser look like everyone else's. Or you can randomise: give a slightly different answer each time so your fingerprint never stays the same. Hiding things (blocking scripts, faking an unusual user agent) often backfires, because being unusual is itself identifying.

  • Tor Browser blends in. Every user gets the same window size (rounded), fonts, time zone and user agent. It's the strongest option, but sites can usually tell you're using Tor.
  • Mullvad Browser applies Tor Browser's anti-fingerprinting, without the Tor network.
  • Brave randomises. It adds small per-site, per-session noise to canvas, WebGL and audio, so your hash differs on every site.
  • Firefox blocks known fingerprinting scripts by default, and adds randomisation in strict mode and private windows. The privacy.resistFingerprinting setting turns on Tor-style uniformity, but it breaks some sites.
  • Safari presents a simplified system profile to every site, and adds noise in private browsing.
  • Content blockers like uBlock Origin block many fingerprinting scripts by their address. This works whatever your fingerprint is.

The ad and fraud-prevention industries keep inventing new signals, and browsers keep closing them. No defence is perfect. Using a mainstream, up-to-date browser with its protections turned on goes a long way.

Further reading

  • Cover Your Tracks (EFF): compares your fingerprint against other visitors, so it can estimate how unique you are. This page can't, because it keeps nothing.
  • AmIUnique: a similar research project with published papers.
  • Mitigating Browser Fingerprinting in Web Specifications (W3C): how standards authors try to avoid creating new signals.
  • JA4+: the JA4 specification, and related fingerprints for servers, HTTP and SSH.
  • TrackMe: shows your TLS and HTTP/2 fingerprints in full detail.
  • FingerprintJS: an open-source fingerprinting library. Reading its source is a good way to see these techniques in practice.
